# 커뮤니티 신고 처리

## 배포

1. 기존 DB를 백업하고 `db/20260928_community_report_moderation.sql`을 공용 DB에 적용합니다.
2. gongbu-eong-admin과 gongbu-eong-backend, gongbu-eong-frontend를 함께 배포합니다.
3. 신고 접수, 작성자/신고자 검색, 검토 시작과 처리 이력을 확인합니다.

SQL은 `community_reports.moderation_history` JSONB 배열만 추가합니다. 기존 신고와 처리 메모는 보존되며,
과거에 저장하지 않았던 처리자/조치를 소급하여 만들어 넣지 않습니다. 운영 DB에는 자동 적용하지 않습니다.
`reason_detail`은 기존 컬럼을 사용합니다.

## 조회

- 기본 목록은 처리 대기와 검토 중을 함께 표시합니다.
- 통합 검색 또는 제목/본문, 신고 사유/처리 메모, 대상 작성자, 신고자를 선택해 검색할 수 있습니다.
- 회원 검색은 커뮤니티 닉네임, 닉네임, 표시 이름, 이메일을 각각 조회합니다.
- 사유, 상태, 게시글/댓글/답글 필터와 페이지 이동 시 검색 조건이 유지됩니다.
- 신고 당시 스냅샷과 현재 원문을 구분합니다. 원문이 없어져도 저장된 증거를 조회할 수 있습니다.
- 동일 대상의 다른 신고는 링크로 모아서 확인하며, 한 건의 처리로 다른 신고를 자동 종결하지 않습니다.

## 조치

| 선택 | 신고 상태 | 콘텐츠 변경 |
| --- | --- | --- |
| 검토 시작 | 검토 중 | 유지 |
| 위반 확인 · 숨김 후 종결 | 처리 완료 | status=deleted |
| 위반 없음 · 공개 상태 유지 후 종결 | 위반 없음 | 유지, 자동 복구 안 함 |
| 위반 없음 · 원문 복구 후 종결 | 위반 없음 | status=active |
| 이미 숨김·삭제된 대상 · 종결 | 처리 완료 | 유지; 공개된 대상에는 선택 불가 |
| 재검토 요청 | 처리 대기 | 유지 |

숨김은 물리 삭제가 아닙니다. 댓글은 기존 정책대로 삭제 표시/답글 맥락이 남을 수 있습니다.
복구 시 작성자가 삭제한 내용일 수도 있으므로 별도 확인을 받습니다.
종결된 신고는 재검토 요청을 거친 뒤 다시 처리합니다. 검토 시작 외에는 1~1,000자의 처리 사유가 필수입니다.
회원 정지, 포인트 회수, 자동 알림 발송은 수행하지 않습니다.

## 일관성

- 콘텐츠 변경, 신고 상태, 관리자 ID/이름, 변경 전후 상태, 사유와 시각을 한 트랜잭션으로 저장합니다.
- 일반 회원 ID를 참조하는 기존 reviewed_by에 별도 admin_users의 ID를 넣지 않습니다.
- reviewed_at은 종결 시에만 설정하고 재검토 시 초기화합니다. 이전 종결 내용은 이력에 유지합니다.
- 화면에서 읽은 신고 상태/수정 시각과 대상 상태가 달라지면 409를 반환합니다.
- 사용자의 중복 접수로 검토 중이거나 종결된 신고를 초기화하지 않습니다.
- 다른 사유를 선택하면 기타 상세 입력은 초기화됩니다. 기타는 상세 내용이 필수이며 최대 1,000자입니다.

## 검증

- 관리자: `npm run test:community-reports`
- 백엔드: `npm run test:community`
- 세 프로젝트: `npx tsc --noEmit --incremental false`

테스트는 격리된 메모리 DB를 사용하며 실제 회원 데이터나 신고를 변경하지 않습니다.
